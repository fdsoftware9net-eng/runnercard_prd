# คู่มือเชื่อมต่อ — ส่งข้อมูลที่แก้ไขแล้วเข้าสู่ RunnerPortal (บางแสน10)

สำหรับทีมพัฒนาระบบ **บัตรนักวิ่ง / wallet** เดิม
งานบางแสน10 ปี 2026 · วันแข่ง 13 กันยายน 2026

---

## 1. เรื่องนี้คืออะไร

บางแสน10 ปีนี้ใช้ **ระบบบัตรนักวิ่งและ wallet ตัวเดิม** ไม่ใช่ตัวใหม่ที่กำลังพัฒนาอยู่บน
id.Kadn เพราะตัวใหม่จะไม่เสร็จทันวันแข่ง

ระบบเดิมมีหน้าจอแก้ไขข้อมูลนักวิ่งอยู่แล้ว และเก็บข้อมูลไว้ในฐานข้อมูลของตัวเอง
สิ่งที่ต้องทำเพิ่มคือ **เมื่อแก้ไขข้อมูลนักวิ่งในระบบเดิม ให้ส่งข้อมูลนั้นมาที่ RunnerPortal ด้วย**
ไม่อย่างนั้นรายชื่อผู้เข้าแข่งขันฝั่งเราจะเก่า และหน้างาน expo จะใช้ไม่ได้

**ตัวเชื่อม:** `event` + `year` + **หมายเลข BIB**
เราไม่ใช้รหัสภายในของ Thairun เพราะระบบ wallet ไม่เคยมีรหัสนั้น — สิ่งที่มีคือ BIB
ซึ่งเป็นเลขที่พิมพ์อยู่บนบัตรนักวิ่ง

> ✅ **ตรวจสอบแล้วว่าใช้ BIB เป็นตัวเชื่อมได้จริง** — บางแสน10 ปี 2026 มี 11,500 รายการ
> และมี BIB ที่ไม่ซ้ำกัน 11,500 เลข ไม่มีซ้ำเลยแม้แต่รายการเดียว (นับรวมรายการที่ยกเลิกและเลื่อนสิทธิ์แล้ว)

---

## 2. ⏰ ช่วงเวลาที่เปิดให้ส่งข้อมูล — เรื่องสำคัญที่สุด

การส่งข้อมูลเข้ามาจะเปิดอยู่ **เฉพาะช่วงที่ระบบของท่านเป็นต้นทางข้อมูลจริง** เท่านั้น

| ช่วง | ใครเป็นต้นทางข้อมูล | endpoint นี้ |
|---|---|---|
| ก่อนวันตัดโอน | ผู้จัดแก้ไขใน **ระบบ wallet** | 🟢 เปิด |
| หลังวันตัดโอน | ผู้จัดแก้ไขใน **RunnerPortal** (`/admin/registrations`) | 🔴 ปิด |

เมื่อปิดแล้ว ทุกคำขอจะได้รับคำตอบ:

```json
{ "error": "authority_moved" }
```
พร้อมสถานะ `403` และ **ไม่มีข้อมูลใดถูกแก้ไข**

> 🔴 **`authority_moved` ไม่ใช่ข้อผิดพลาด** แต่คือการจบการเชื่อมต่อตามที่ตกลงกันไว้
>
> - **อย่า retry**
> - **อย่าแจ้งเตือนทีม on-call**
> - **อย่าสับสนกับ `forbidden`** ซึ่งแปลว่า key ตั้งค่าผิด และต้องมีคนมาแก้

วันตัดโอนจะแจ้งให้ทราบล่วงหน้า ฝั่งเราตั้งเป็น "เวลา" ไว้ในระบบ
ดังนั้นมันจะปิดเองตามเวลาที่กำหนด แม้ไม่มีใครอยู่หน้าคอมพิวเตอร์

---

## 3. ภาพรวมการทำงาน

```
ผู้จัดแก้ไขข้อมูลนักวิ่งในระบบ wallet
        │
        ▼
ระบบ wallet รวบรวมรายการที่แก้ไข (ส่งเป็นชุดได้ ไม่เกิน 5,000 รายการ)
        │
        ▼
POST /v1/registrations/edits   ← ลงลายเซ็น HMAC + Idempotency-Key
        │
        ▼
RunnerPortal ตอบกลับผลรายคน (updated / unchanged / not_found / rejected)
```

---

## 4. การยืนยันตัวตน (Authentication)

ใช้วิธี **เดียวกันทั้งหมด** กับที่ Thairun ใช้ — ลงลายเซ็น HMAC-SHA256

รายละเอียดทั้งหมดและ **ตัวอย่างที่มีค่าจริงให้ลองคำนวณตาม** อยู่ใน
[`api-reference.md`](./api-reference.md) หัวข้อ 2 และมีโค้ดตัวอย่างที่รันได้จริงใน
[`samples/`](./samples/)

**ก่อนเขียนโค้ดส่วนอื่น ให้ทำข้อนี้ให้ผ่านก่อน:** รันตัวอย่างในหัวข้อ 2.3 และ 2.4
แล้วให้ได้ลายเซ็นตรงกับที่เอกสารเขียนไว้ ถ้ายังไม่ตรง อย่าเพิ่งเขียนต่อ

### ⚠️ 3 จุดที่มักพลาด

1. **ลายเซ็นคำนวณจาก body ดิบ (raw bytes)** ที่ส่งจริง ไม่ใช่จาก object ที่แปลงกลับมาใหม่
   ถ้า serialize ใหม่ ลำดับ key หรือช่องว่างอาจเปลี่ยน แล้วลายเซ็นจะไม่ตรง
2. **`Idempotency-Key` จำเป็นต้องมีเสมอ** ถ้าไม่ส่งจะได้ `400`
3. **นาฬิกาเครื่องต้องตรง** ลายเซ็นมีอายุจำกัด ถ้าเวลาเพี้ยนจะได้ `401`

## 5. รูปแบบข้อมูลที่ส่ง

```jsonc
POST /v1/registrations/edits

{
  "event": "bangsaen10",
  "year": 2026,
  "dry_run": true,
  "records": [
    { "bib_number": "10234", "first_name": "สมชาย", "shirt_size": "L" },
    { "bib_number": "10235", "registration_status": "cancelled" }
  ]
}
```

ส่ง **เฉพาะฟิลด์ที่ต้องการแก้** ไม่ต้องส่งทั้งระเบียน

---

## 6. 🔴 "ไม่ส่ง" / "ส่ง null" / "ส่งค่าที่อ่านไม่ออก" — สามอย่างนี้ต่างกัน

นี่คือกฎที่สำคัญที่สุดในเอกสารนี้

| ท่านส่ง | เราทำ |
|---|---|
| **ไม่ส่งฟิลด์นั้นมาเลย** | ไม่แตะต้อง คงค่าเดิมไว้ |
| **ส่ง `null`** | ล้างค่าในช่องนั้น |
| **ส่งค่าที่เราอ่านไม่ออก** | **ปฏิเสธเฉพาะรายการนั้น** พร้อมบอกเหตุผล |

ข้อสุดท้ายสำคัญมาก — เรา **ไม่** เปลี่ยนค่าที่อ่านไม่ออกให้เป็นค่าว่างเงียบ ๆ
เพราะถ้าโปรแกรมฝั่งท่านมีบั๊ก เราต้องบอกท่าน ไม่ใช่กลืนมันลงฐานข้อมูลเรา

### `registration_status` ต้องตรงตัวอักษรเท่านั้น

รับเฉพาะ 5 ค่านี้: `registered` · `cancelled` · `transferred` · `deferred` · `no_show`

คำอื่นจะถูกปฏิเสธ **ไม่ใช่** เดาให้ เช่นถ้าพิมพ์ `withdrawn` มา เราจะปฏิเสธรายการนั้น
ไม่ใช่ตีความเป็น `registered` — เพราะการเดาผิดหมายถึงนักวิ่งที่ยกเลิกไปแล้วกลับมามีสิทธิ์วิ่งอีกครั้งโดยไม่มีใครรู้

## 7. สิ่งที่แก้ไม่ได้ และเหตุผล

| แก้ไม่ได้ | เพราะ |
|---|---|
| **`bib_number`** | มันคือกุญแจที่ใช้ระบุตัวคน ถ้าเปลี่ยนได้ คำสั่งถัดไปจะไม่รู้ว่าหมายถึงใคร และการเปลี่ยน BIB จริงต้องแจ้งฝ่ายจับเวลาก่อนปล่อยตัว มิฉะนั้นนักวิ่งคนนั้นจะไม่ถูกจับเวลาเลย |
| **ลบเลขบัตรประชาชน/พาสปอร์ตที่มีอยู่แล้ว** | ลบแล้วนักวิ่งจะหลุดออกจากประวัติการวิ่งของตัวเอง สิทธิ์เสื้อรางวัล และการนับปี — **แก้ไขเป็นเลขอื่นได้** แต่ลบทิ้งไม่ได้ |
| **ลบชื่อจนไม่เหลือชื่อเลย** | ต้องเหลือชื่อในช่องใดช่องหนึ่งจาก 4 ช่อง (ไทย/อังกฤษ ชื่อ/นามสกุล) |
| **`raw_data`** | เป็นข้อมูลดิบทั้งแถวจากไฟล์ต้นทาง รวมข้อมูลสุขภาพ — ไม่เปิดให้เขียนหรืออ่าน |

ถ้าส่งฟิลด์ที่ key ของท่านไม่มีสิทธิ์เขียนมา เรา **ไม่ปฏิเสธทั้งรายการ**
แต่จะข้ามฟิลด์นั้นและส่งชื่อกลับมาใน `ignored` เพื่อให้ท่านเห็นว่า mapping อาจผิด

## 8. คำตอบที่ได้รับ

คำขอที่รูปแบบถูกต้องจะได้ `200` เสมอ พร้อมผลลัพธ์**รายคน**
รายการที่ผิดหนึ่งรายการ **จะไม่ทำให้รายการที่ถูกต้องเสียไปด้วย**

```jsonc
{
  "dry_run": false,
  "batch_id": "…",
  "received": 3, "updated": 1, "unchanged": 1,
  "not_found": 1, "ambiguous": 0, "rejected": 0,
  "results": [
    { "bib_number": "10234", "outcome": "updated", "changed": ["first_name"] },
    { "bib_number": "10235", "outcome": "unchanged" },
    { "bib_number": "99999", "outcome": "not_found" }
  ]
}
```

| `outcome` | ความหมาย | ต้องทำอะไร |
|---|---|---|
| `updated` | แก้ไขเรียบร้อย | — |
| `unchanged` | ค่าที่ส่งมาตรงกับที่เรามีอยู่แล้ว | — |
| `not_found` | ไม่มี BIB นี้ในงานนี้ | ตรวจสอบว่า BIB ถูกต้องหรือไม่ |
| `ambiguous_bib` | BIB นี้ตรงกับมากกว่า 1 รายการ เราไม่เดา | **แจ้งเรา** ผิดปกติ |
| `rejected` | ดูเหตุผลใน `reason` | แก้ที่ต้นทางแล้วส่งใหม่ |

### คำตอบที่ปฏิเสธทั้งคำขอ (ไม่มีอะไรถูกแก้เลย)

| HTTP | ความหมาย |
|---|---|
| `400` | รูปแบบข้อมูลไม่ถูกต้อง ดูที่ `detail` |
| `403 authority_moved` | ปิดรับแล้ว — ดูหัวข้อ 2 |
| `403 forbidden` | key ไม่มีสิทธิ์ หรือระบุ event/ปี ที่ไม่ตรงกับ key |
| `409` + `duplicate_bib_in_payload` | ส่ง BIB เดียวกันซ้ำใน request เดียว เราไม่รู้ว่าอันไหนคือคำตอบสุดท้าย |
| `409 idempotency_key_reused` | ใช้ `Idempotency-Key` เดิมกับข้อมูลที่ต่างออกไป |

---

## 9. 🔴 ใช้ `dry_run: true` ก่อนเสมอ

ส่ง `"dry_run": true` จะได้รายงานหน้าตาเหมือนกันทุกอย่าง แต่ **ไม่เขียนข้อมูลจริง**

ให้ใช้ทุกครั้งที่ส่งชุดข้อมูลรูปแบบใหม่เป็นครั้งแรก
ตรวจดูว่า `updated` และ `not_found` เป็นตัวเลขที่คาดไว้ แล้วค่อยส่งจริง

---

## 10. การส่งซ้ำ (retry)

ทุกคำขอต้องมี header `Idempotency-Key` เป็นค่าที่ไม่ซ้ำต่อหนึ่งชุดข้อมูล

ถ้าคำขอ timeout แล้วท่านไม่แน่ใจว่าข้อมูลเข้าหรือยัง **ให้ส่งซ้ำด้วย key เดิม**
เราจะส่งรายงานเดิมกลับไป และ **ไม่แก้ไขข้อมูลซ้ำ**

⚠️ ถ้าใช้ key เดิมแต่เนื้อหาต่างกัน จะได้ `409` — เพราะนั่นแปลว่าโปรแกรมฝั่งท่านมีบั๊ก
และการตอบรายงานเดิมกลับไปจะปิดบังบั๊กนั้นไว้

---

## 11. ขั้นตอนเริ่มต้น

1. แจ้งช่วง IP ของเซิร์ฟเวอร์ที่จะเรียก API และผู้ติดต่อฝ่ายเทคนิค
2. เราออก key สำหรับ **ทดสอบ (sandbox)** ให้ — secret จะแสดงครั้งเดียว
   ให้เก็บใน secret manager **ห้ามใส่ใน source control**
3. ทำลายเซ็นตัวอย่างในหัวข้อ 2.3 และ 2.4 ของ `api-reference.md` ให้ตรงก่อน
4. ทดสอบด้วย `dry_run: true`
5. แจ้งเรา แล้วเราจะออก key จริงและ **เปิดช่วงเวลาส่งข้อมูล** ให้

> ⚠️ ข้อ 5 มีสองขั้นตอนแยกกัน: การมี key ไม่ได้แปลว่าส่งข้อมูลได้ทันที
> ต้องเปิดช่วงเวลาให้ด้วย — ออกแบบไว้แบบนี้เพื่อให้ท่านทดสอบระบบได้ก่อนที่จะแตะข้อมูลจริง

- `request_id` จาก log ฝั่งท่าน

- endpoint ที่เรียก
- key id ของท่าน
